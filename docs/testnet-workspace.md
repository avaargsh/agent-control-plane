# Testnet workspace and recovery

The verifier (`4321`) remains read-only. A separate development server (`4322`) compiles the repository's `AgentLedger.sol` with Solidity 0.8.24, optimizer 200 and the Shanghai EVM target, then serves a wallet-assisted deployment UI. It does not receive or hold private keys. The wallet submits each user-confirmed transaction.

## Step four: read chain state

After the wallet returns a task-creation transaction hash, the workspace automatically calls the same-origin `GET /api/task-creation` endpoint. The server checks network 10143, creation calldata, sender, recipient, zero native-token value, successful receipt, `TaskCreated` event, canonical block and the current `getTask` result. The browser compares that observation against its prepared task, including the exact input hash, budget and nonce when available.

On success it opens `/studio#mode=live&contract=…&taskId=…` on the **same port**. Studio independently calls `GET /api/task` and displays the actual ledger state. The fourth step does not require the MetaMask provider. Both routes reuse the standalone verifier's read-only handler; no generic RPC forwarding or write endpoint is added.

Pending receipts are checked at most six times with 1.5 seconds between checks. The browser limits each HTTP observation to 15 seconds. Reverts, identity mismatches, changed blocks and RPC errors remain visible failures; no retry broadcasts a transaction. Manual **检查任务创建交易** performs a single observation and leaves a Studio link available without automatic navigation.

An existing prepared task can be verified without connecting a wallet by opening `/#task=prepared&transactionHash=0x…&verify=1` on the workspace. The prepared artifact must match the browser's existing task record; the link never overwrites another task or submits a transaction. The backend independently validates the supplied hash before navigation.

## What is persisted

Compilation writes `out/testnet-deploy/AgentLedger.json` with ABI, creation/runtime bytecode, immutable-reference offsets, compiler settings and source SHA-256. The browser stores deployment and task transaction journals in localStorage for the current origin. Changing browsers, ports or forwarding origins does not transfer these records.

A journal saves the exact sender, recipient, calldata, zero value and nonce **before** requesting a signature. A successful response adds the transaction hash. Only an explicit user cancellation clears the pending signature intent. Other errors preserve it and block automatic retry. Concurrent clicks in the same page cannot open multiple signature requests. This is a browser-local journal, not distributed transaction coordination.

The deployment record retains the constructor's `paymentRecorder`. The task record retains the exact UTF-8 input text, SHA-256, generated bytes32 task ID and atomic budget cap. After refresh, submitted inputs are restored and locked. Download records before clearing browser site data.

## Recover an interrupted transaction

1. Reopen the same deployment-page origin and connect the wallet to Monad Testnet.
2. If a transaction hash was saved, click its check button.
3. If the signature request was saved but its response was lost, open MetaMask activity and copy the original transaction hash into the recovery field.
4. Check the original transaction. Recovery validates sender, recipient, calldata, nonce, value, successful receipt and canonical block before trusting it.
5. Deployment checks additionally reconstruct runtime bytecode with the immutable recorder value. Task checks use the independent read-only service and compare creator, input hash, budget and valid lifecycle status. A task transaction can be checked without connecting MetaMask.

Unconfirmed, reverted, replaced or mismatched transactions do not automatically unlock another submission. Inspect wallet activity before deliberately clearing or migrating the browser record. The app currently retains one deployment and one created task per browser origin; multi-deployment/history management is not implemented.

The runtime check demonstrates agreement with the compiled local source. It does **not** add external review, prove finality, verify USDC Transfer/AuthorizationUsed, or satisfy the empty PR-reviewed deployment registry.

## Wallet troubleshooting

- **No MetaMask detected:** use a browser with the extension enabled; the page supports EIP-6963 and legacy multi-provider detection. Mobile QR connection is not implemented.
- **Address visible, wrong network:** address authorization succeeded; use the separate switch/add-network button. Deployment is disabled until chain ID 10143 is selected.
- **No account returned:** unlock MetaMask and authorize an account for this exact site origin.
- **Pending request:** resolve or cancel the existing request in the extension instead of repeatedly clicking connect.
- **Remote development:** forward port 4322 for the full workflow; its Studio links stay on that same origin. Forwarding 4321 is optional for standalone Studio access.

## Local EVM browser test

This test uses real headless Chrome, real Solidity creation bytecode and a test wallet adapter backed by **local Anvil unlocked accounts**. It never uses the public wallet, broadcasts to a public chain, or reports public Testnet payment acceptance. It refuses non-loopback URLs and checks `web3_clientVersion` for Anvil before running.

Prerequisites: system Chrome/Chromium, Python `playwright`, installed workspace dependencies, and Anvil (or its official npm package). Start an isolated EVM and a deployment workspace configured for that local EVM in separate terminals; these ports do not interfere with the public-Testnet workspace on 4322:

```bash
npm exec --yes --package=@foundry-rs/anvil@1.7.1 -- \
  anvil --host 127.0.0.1 --port 18545 --chain-id 10143 --silent
```

```bash
MONAD_RPC_URL=http://127.0.0.1:18545 AGENTLEDGER_DEPLOY_PORT=14422 \
  node examples/verifier/tools/serve-testnet-deploy.mjs
```

```bash
npm run test:browser:anvil
```

The test covers missing-wallet guidance, EIP-6963 discovery without `window.ethereum`, deployment, runtime/recorder checks, task creation, automatic step-four navigation, refresh recovery, walletless Studio lookup and mobile overflow. Screenshots are written to `out/testnet-deploy/local-evm-*.png`; `local-evm-browser-acceptance.json` records the local transactions and check results with explicit local-only classification. Environment overrides are `AGENTLEDGER_ANVIL_RPC`, `AGENTLEDGER_DEPLOY_URL` and `AGENTLEDGER_CHROME_PATH`; service URLs must remain loopback. The deployment helper's `MONAD_RPC_URL` must point to the same local Anvil instance.

Public Testnet deployment and task creation still require wallet confirmations. Full funded x402 acceptance requires the independent evidence documented in [live Testnet observation](live-testnet-observation.md).
